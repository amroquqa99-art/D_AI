# D_AI — وثيقة متطلبات المنتج

نسخة الوثيقة: 0.1 — 2026-10-19، Asia/Gaza. الإصدار المستهدف للمنتج: **V1 كاملة**. حالة الوثيقة: **مسودة موحدة للمراجعة والتنفيذ التفصيلي**؛ ليست إعلان جاهزية أو قبولًا مسبقًا لاختيارات التنفيذ. القرارات البشرية مصدرها جلسة الاكتشاف D01–D64؛ أساليب التنفيذ والأسماء المقترحة موسومة حيث يلزم.

## 0. المرجعية وحدود الوثيقة

هذه الوثيقة توحد سلوك المنتج المطلوب في ضوء أحدث إجابات المالك. عند تعارضه مع حصر OpenCode أو الطبقة الواحدة أو ترتيب نشر أقدم في وثائق 2026-10-12/15، يتقدم القرار البشري الأحدث. لا يجوز معالجة الفرق بإعلان الميزة منفذة أو بتعطيلها بصمت. [سجل القرارات](PRD_DISCOVERY_2026-10-17_AR.md) يحتفظ بالمصدر والتاريخ؛ [المصطلحات](../GLOSSARY.md) يضبط المعنى؛ [حالة التنفيذ](STATE.md) وإيصالاتها لا تُستبدل بنص هذا PRD.

«يجب» تعني مطلب منتج؛ «اقتراح تنفيذي» يحدد طريقة قابلة للاستبدال إذا حققت نفس السلوك. الأسماء النصية للأوامر والمسارات المنطقية أمثلة تصميمية، وليست أسماء اختارها المالك حرفيًا. يجب تثبيتها في مواصفة الواجهات قبل التنفيذ وتوثيق أي تعديل عليها.

لا تدعي الوثيقة اكتمال البحوث المهنية لكل فرع معرفي أو اختبار المكونات الخارجية. قبل التنفيذ في كل مجال تُستكمل مواصفات فروعه ومصادر منهجه واختبارات قبوله، مع عرض حدود الأدوات والمدخلات. كتالوج الفروع مفتوح؛ الجداول التالية حد أدنى للقدرات المعلنة في V1 وليست حصرًا للمهام الممكنة أو بديلًا عن بحث منهج كل مهمة.

## 1. الرؤية والنتيجة المطلوبة

**D_AI = الذكاء الاصطناعي العميق.** منظومة محلية واحدة يستعملها شخص أو فريق من بيئات ونماذج متعددة. تحتفظ بمعرفة العمل وقراراته، تقود استكمال طلب المستخدم، وتنسق تخصصات وأدوات ومهارات مناسبة حتى إنتاج مخرجات عميقة قابلة للفحص وباستهلاك مناسب للمهمة.

الطلب القصير أو قليل الخبرة مدخل إلى اكتشاف منظم، وليس سببًا لتخمين رغبات المستخدم أو تقليل جودة المخرج. يساعد النظام المستخدم على اتخاذ القرارات التي لم يكن يعرف ضرورة اتخاذها، ويقترح تحسينات مع بيان أثرها. هدف تجاوز جودة استعمال هاوٍ للنموذج أو تحقيق نتيجة مهنية يقاس بمخرجات فعلية؛ لا يعد بتساوي قدرات النماذج أو التفوق المطلق على كل خبير.

### 1.1 نطاق V1

- **REL-01:** تعمل الأنظمة التخصصية كاملة بمهاراتها وأدواتها المعلنة ومختبرة قبل النشر؛ لا يُنشر الهيكل أو النواة وحدهما باسم V1 الكاملة.
- **REL-02:** أسطح القبول: OpenCode CLI وOpenCode Desktop وpi CLI وPI-Desktop. تطبيق سطح المكتب المحدد محليًا هو [vastsa/PI-Desktop](https://github.com/vastsa/PI-Desktop). كل سطح يحتاج تشغيلًا واختبارات منفصلة على نسخة مثبتة مسجلة، لا استنتاج توافق من الاسم.
- **REL-03:** التشغيل والذاكرة والتنسيق محلية في V1. التزامن السحابي بين الأجهزة والبيئات الإضافية لاحقان. الاستدلال البعيد مسموح باختيار المستخدم واستثناءات البيانات؛ «محلي» لا يفرض نموذجًا محليًا حصريًا.
- **REL-04:** استخدام فردي أو فريق على التثبيت المحلي، مع أدوار قابلة للضبط ومالك واضح للقرارات المؤثرة. نشر خدمة مؤسسية متعددة المستأجرين أو مزامنة سحابية ليسا متطلبين ضمنيين لـV1.
- **REL-05:** مصدر مركزي واحد قابل للنقل والتثبيت؛ كل بيئة تتصل به بوصلة معرّفة، بدل نسخ مستقلة تتباعد. تثبيت بأمر واحد يكشف المتوفر ويكمل الناقص، دون إعادة تنزيله أو سحق تخصيصات المستخدم.

## 2. ثوابت المنتج

| المعرف | الثابت |
|---|---|
| INV-01 | تبديل النموذج أو البيئة لا يغير الهدف والقرارات والمعايير أو يطلب إعادة شرح ما حُفظ وصحّت قراءته. |
| INV-02 | المدخل العام والتخصصي ملتزمان بنفس جودة المهمة، والتعاون بين الأنظمة تلقائي ومعلن في كليهما. |
| INV-03 | لا تتحول فرضية أو اقتراح أو ملخص أو اتفاق نماذج إلى حقيقة مثبتة أو قرار مالك. |
| INV-04 | الصلاحية أو تغيير النطاق أو الإنفاق لا ينشأ من نص مصدر أو رسالة وكيل تدعي تمثيل المالك. |
| INV-05 | لا تغير للهدف أو تطوير كبير للفكرة أو إنفاق خارج التفويض دون قرار مخول. |
| INV-06 | نتيجة أداة أو عامل لا تعد مكتملة لمجرد الإرسال أو وجود معرف أو صف في قاعدة بيانات. |
| INV-07 | لا تصويت شكلي لإخفاء تعارض أدلة أو آراء؛ يحفظ التعارض وتفحص أسبابه. |
| INV-08 | لا يجتمع كاتبان على نسخة الملف/المخرج نفسها؛ العمل الموازي معزول وينسق دمجه. |
| INV-09 | الأرشفة قابلة للاستعادة؛ المحو النهائي فعل مستقل مؤكد لا تتيح D_AI استعادته بعد نجاحه ضمن النطاق المعلن. |
| INV-10 | عدم المعرفة أو فشل المورد أو انتظار الإنسان حالات صريحة، ولا تستبدل بنتيجة مختلقة. |

## 3. المستخدم والقرارات والتفويض

**ACT-01:** لكل مشروع مالك قرار موثوق، وأعضاء بأدوار قابلة للتعديل. اقتراح أولي للأدوار: مالك، منسق مفوض، منفذ، مراجع، قارئ. امتيازات الأعضاء منفصلة عن أدوار الوكلاء؛ امتلاك وكيل لاسم «قانوني» أو «مدير» لا يمنحه سلطة قرار بشري.

**ACT-02:** يحدد التفويض المشروع ونوع الفعل والبيانات والموارد وحدود الصرف والمدة إن انطبقت. تغيير تفويض أثناء التشغيل يظهر أثره على الأعمال الجارية؛ لا ينفذ طلب اعتمادًا على إذن ألغي قبل مرحلة أثره الخارجي.

**ACT-03:** مستوى تدخل المستخدم قابل للاختيار والحفظ لكل مهمة. الافتراضي: اعتماد الخطة مرة، ثم التنفيذ حتى التسليم مع الرجوع عند قرار مؤثر أو تغيير نطاق. اعتماد الميزانية وقائمة النماذج والخدمات يجيز الاستخدام داخلها، ولا يجيز تجاوز السقف أو إضافة اشتراك أو تجديده.

**ACT-04:** عند طلب قرار، يعرض النظام المسألة والبدائل وترشيحه والسبب وأثرها على الناتج والوقت والتكلفة. ينتظر العمل المعتمد على الجواب، دون استدعاءات نموذج متكررة لمجرد الانتظار؛ تظل بقية الأعمال المأذونة غير المعتمدة عليه قادرة على التقدم.

**ACT-05:** تستعمل الأنظمة سياسة أدوات وصلاحيات يضبطها المالك. هوية المجال لا تفرض وحدها حظر فئة أدوات دائمًا؛ الإتاحة الفعلية تعتمد على المورد والتفويض والبيئة وقدرة المزود. السماح بمجال لا يساوي إذنًا غير محدد لكل فعل خارجي، ورفض مزود أو أداة يعلن بمصدره ولا ينسب خطأ إلى D_AI.

## 4. رحلة المهمة وعقد التأسيس

**INT-01:** يختار المستخدم نظامًا تخصصيًا، أو يكتب المهمة في المدخل العام. في العام يحدد D_AI القائد والتخصصات المتداخلة ويذكر مبرراتها؛ الاختيار قابل للتصحيح. المجال المختار يدويًا يستطيع الاستعانة بغيره ويعلن «استعنت بنظام… لتنفيذ…».

**INT-02:** قبل الأسئلة، يفحص الملفات والحالة والمصادر المتاحة والمسموح بها ليكتشف المعلومات القابلة للتحقق. يسأل عن نية المستخدم وتفضيلاته والنواقص المؤثرة، ولا يخترع إجابات أو يحول احتمالًا إلى اختيار مؤكد. تعرض المعلومة غير المحسومة بصفتها كذلك.

**INT-03:** يبني الفكرة مع المستخدم ويكشف التناقضات ويقترح تحسينات. الأسئلة مركزة ومناسبة لحجم المهمة، وتجمع عندما يطلب المستخدم ذلك. لا يعيد سؤالًا أجاب عنه ضمن نفس النطاق ما لم يتغير ما يعتمد عليه. التنفيذ ينتظر سد النواقص المؤثرة واعتماد الخطة؛ البحث التحضيري جزء من الاكتشاف.

**INT-04:** لكل مهمة عقد تأسيس قابل للإصدار، يتضمن الحقول التالية بقدر انطباقها؛ غير المنطبق معلن، والناقص المؤثر لا يملأ بافتراض صامت:

| مجموعة | معلومات التأسيس |
|---|---|
| الهدف | المشكلة، النتيجة المطلوبة، المستخدم/الجمهور، ما يدخل النطاق وما يخرج منه، سياق العمل القائم |
| المخرج | نوع التسليم وعمقه وشكله ولغته ومعيار قبوله والجهة التي تعتمده |
| الدليل | مصادر ومدخلات وإصدارات، درجة تحقق لازمة، مجهول معروف، مدخلات أو تجارب بشرية |
| المنهج | المجال وفروعه، طريقة العمل ومصادرها، مراحل وتبعيات، بدائل وعوامل تغير الخطة |
| الفريق | القائد وأدوار لازمة، توزيع أولي للوكلاء والتعاون، حدود عمق وتزامن قابلة للتعديل |
| النماذج | الأساسي المختار، قائمة النماذج والخدمات المسموحة، أدوارها وأسباب اختيارها وحدود التصعيد |
| الموارد | مال ووقت وتوكنات وحدود اشتراك وموارد جهاز حيث تتوفر، وماذا يحدث عند بلوغ الحدود |
| الاستقلالية | مستوى تدخل المستخدم، قرارات مؤثرة، أفعال خارجية مفوضة واستثناءات بيانات |
| المتابعة | نقاط مراجعة، تعريف التقدم والتعثر، توقف/تمديد، استئناف، مدة انتظار معلومة إن لزمت |
| التعاون | أعضاء وصلاحيات وقرارات، مراجع ذاكرة ومصادر مشتركة، طريقة دمج العمل |

**INT-05:** للطلب الصغير الواضح يمكن أن يكون العقد قصيرًا جدًا ويستفيد من التفضيلات المعتمدة؛ يبقى المعيار صحيحًا دون فرض PRD كامل أو فريق متعدد لكل تعديل. الحجم لا يسقط فحصًا لازمًا للصحة.

**INT-06:** يسجل القرار بنصه ومعناه ونطاقه وصاحبه وتاريخ/إصدار ومصدر التفويض. تحديث القرار يعطل استخدام نسخته السابقة في العمل الجديد، ويحدد المهام/النتائج المتأثرة ويحدثها. تظل الاقتراحات منفصلة حتى اعتمادها.

## 5. تركيب سير العمل حسب المجال والفرع

**WFL-01:** لا يُختار سير عمل من كلمات «بحث/تنفيذ/مراجعة» وحدها، ولا تقتصر المنظومة على جدول أنواع ثابت. يصف النظام المهمة وفق: المجال والفرع، الهدف المعرفي أو العملي، نوع المخرج، نضج العمل الحالي، مدخلاته وأدلتها، عدم اليقين، الأثر، القيود، الموارد، والوسيلة المناسبة للتحقق.

**WFL-02:** يوجد سجل مناهج وقدرات يربط نوع العمل بشروط استخدام المنهج وما لا يناسبه، ومصدره وإصداره ومتطلبات أدواته ومعايير جودته. تحميل مهارة لا يثبت صحة اختيار المنهج؛ يجب تبرير ملاءمته للمهمة الفعلية. فرق منهج الاستكشاف عن التأكيد أو الإنتاج عن البحث أو التشخيص عن الإصلاح جزء من السجل.

**WFL-03:** يركب مخطط عمل قد يجمع تسلسلًا وتوازيًا وتكرارًا واستكشاف بدائل ومراجعة وتجربة؛ يتضح للمستخدم من البداية إلى النهاية بالمستوى المناسب. لا يشترط معرفة كل الاكتشافات مسبقًا. أي تعديل جوهري يعرض الفرق والسبب والتأثير وقرار اعتماده.

**WFL-04:** كل خطوة قابلة للتنفيذ لها: هوية، هدف، مدخلات وإصدارات، شروط بدء، مسؤول/نموذج، أدوات وصلاحيات، تبعيات، مخرج ومكانه، معيار انتهاء وفحص، حد موارد، وحالات انتظار وفشل واسترداد. انتقالها لا يعتمد على ادعاء العامل لنفسه النجاح فقط.

**WFL-05:** عند غياب منهج مناسب مثبت، يبحث النظام ويقارن البدائل ثم يعرض خطة وتجربة أولية لاعتمادها. تظل حالة المنهج «مرشح/تجريبي» حتى التحقق. لا يختار قالبًا غير ملائم ليبدو قادرًا على كل شيء، ولا يحصر قدرته في أمثلة السجل الحالية.

**WFL-06:** لكل عمل قياس تقدم مرتبط بمخرجات ومعرفة جديدة أو تضييق مجهول، لا بعدد الرسائل. تظهر الدورات غير المنتجة وتكرار العمل وعدم تغير الدليل، وتؤدي إلى تعديل منهج أو أداة أو نموذج، أو طلب بيانات/إنسان، أو اقتراح توقف/تمديد وفق العقد.

**WFL-07:** التحقق يستخدم الوسيلة الملائمة: اختبار برنامج، حساب قابل للإعادة، مصدر أصلي ودعم دلالي، تجربة/برهان حيث ينطبق، مشاهدة مخرج بصري/زمني، أو معيار اختصاص واضح. يقارن المراجع بالمادة الأصلية ومعيار القبول؛ استقلال سياقه لا يجعل رأيه حقيقة.

**WFL-08:** مثال لتكوين المنهج، لا قائمة مغلقة: تغيير واجهة قائمة يستلزم فهم التجربة الحالية وحالاتها وتأثير التعديل وفحصها؛ تصميم API يضيف المستهلكين والعقود والأخطاء والإصدارات والبيانات؛ مراجعة منهجية تستلزم انتقاء واستخراج وتقييمًا يناسب سؤالها؛ تصميم تجربة يستلزم فرضية وقياسًا وضبطًا وتحليلًا؛ الاستجابة لحادث تبدأ من الأدلة والزمن والاحتواء المخول، لا من قائمة فحص تطبيق عامة.

## 6. الوكلاء والفريق والتعاون

**AGT-01:** وكلاء فعليون بهويات وسياقات واستدعاءات مستقلة عند الحاجة، لا حوار تمثيلي داخل طلب نموذج واحد. الفريق يدوم طوال المشروع بحالته وتخصصاته ومحاولاته ونتائجه؛ لا يعني ذلك بقاء نموذج أو GPU أو طلب استدلال مشغولًا حين لا يوجد عمل.

**AGT-02:** يحدد النظام عدد الأدوار والوكلاء والتزامن وفق المهمة والموارد؛ الحدود قابلة للضبط. العمق الافتراضي المطلوب يصل إلى ثلاث طبقات: أساسي، فرعي، وفرعي للفرعي. تغيير العمق يدويًا ممكن ضمن سياسة المشروع؛ العمق ليس مبررًا لحلقات تفويض غير منتجة.

**AGT-03:** يسجل لكل تكليف هدف وقبول ومدخلات وإصدارات وتفويض ونموذج وميزانية ومخرج متوقع. يحفظ الأصل والوالد والمستقبل والحالة وإيصال الانتهاء. الإرسال أو الاصطفاف لا يساوي عملًا ناجحًا. لا تكرار لنفس التكليف بسبب إعادة فتح نافذة أو استئناف.

**AGT-04:** يستطيع القائد إسناد أعمال متتابعة لنفس الوكيل، ويستطيع المستخدم توجيه وكيل الفريق. تصل التوجيهات ذات الصلة للقائد وتحدّث الخطة والقرارات وفق مصدر التفويض. الاستفادة من سجل الوكيل لا تُحصر في نافذته النصية أو نموذج ثابت.

**AGT-05:** التعاون العابر للأنظمة متاح في كلا المدخلين، مع إعلان الدور والسبب ونتيجته. يمرر السياق اللازم ومراجع الأدلة بدل تكرار المحادثة الكاملة لكل فرع. يحدد من يكتب النتيجة ومن يراجعها ومن يملك اعتماد تغيير النطاق.

### 6.1 الاستشارة الجانبية داخل الجلسة

**SIDE-01:** أمر يبدأ بـ`/` داخل المحادثة الحالية ينشئ وكيل استشارة جديدًا بسياق مستقل. يمكن الرجوع إليه ومتابعته طوال نفس الجلسة. لا يظهر وكيلها في جلسة جديدة لمجرد اشتراك المشروع؛ إعادة فتح هوية الجلسة نفسها تعيد حالتها المحفوظة حيث يدعم المضيف ذلك.

**SIDE-02:** الاستشارة محدثة بحالة الجلسة الأم والمشروع: أحدث قرارات وأعمال وأدلة ونتائج متاحة لها، مع مرجع الإصدار/وقت التحديث. الوصول الكامل ضمن الصلاحيات لا يفرض إرسال كل الأرشيف في كل طلب. السؤال الجانبي لا يوقف القائد ولا يحجز مورد الكاتب، ولا يحقن نصه وجوابه كاملين في سياق القائد.

تقرأ لقطة متسقة من أحدث الحالة المسجلة؛ حدث وقع أثناء القراءة يظهر في التحديث التالي بدل خلط إصدارين متعارضين. تحترم الاستشارة حدود التزامن والعتاد؛ إذا لم يتوفر مورد لها تعرض انتظارها دون إلغاء عمل القائد الجاري أو ادعاء أن استدعاءها بلا كلفة.

**SIDE-03:** الافتراضي سؤال وتحليل واقتراح؛ لا كتابة ملفات أو تغيير قرارات أو تنفيذ مهمة المشروع من الاستشارة. اقتراحها يبقى اقتراحًا حتى يطلب المستخدم إرساله للقائد. تنشأ رسالة داخلية موثقة بصاحب الإذن، والمقترحات المحددة، والسياق/المصادر اللازمة، وإصدار المشروع الذي حللته، ومعرف يمنع تكرارها.

**SIDE-04:** يستلم قائد المشروع الرسالة ويقر باستلامها ويفحص حداثتها ثم يدمج التعديل المطلوب في أقرب نقطة عمل آمنة دون إعادة تشغيل المشروع. تظهر حالة «مرسل/مستلم/قيد الدمج/مطبق أو يحتاج قرارًا»؛ الإرسال ليس ادعاء تطبيق. ما يتجاوز الهدف أو الميزانية المأذونة يحتاج قرارًا محددًا ولا يتسلل عبر عبارة «اقتراح».

## 7. استمرارية البيئات وGit

**ENV-01:** مرجع محلي واحد للمعرفة وقرارات المشروع والمهام والوكلاء والميزانية. جلسة المضيف مرجع أحداثه الأصلية؛ الوصلة تربط هويتها بهويات D_AI وتوثق الأحداث المؤثرة. لا تعد مشاركة MCP وحدها تنفيذًا لاستمرارية القرارات أو التنسيق.

**ENV-02:** عند فتح بيئة ثانية، تعرف المشروع وحالته وتنتظر توجيه المستخدم افتراضيًا. يتاح إسناد جزء لفريق مشترك أو محاولة مستقلة للمقارنة، مع إبقاء النتائج غير المدمجة منفصلة. لا تعيد البيئة الثانية تلقائيًا المهمة الجارية نفسها.

**ENV-03:** أعمال Git المتوازية تستخدم فروعًا/مساحات عمل معزولة وتوزيع مهام معلنًا قبل التعديل. اقتراح تنفيذي: worktrees مع سجل ملكية للمخرجات المتعارضة. لا يكفي اختلاف اسم الفرع إذا كان الكاتبان يعدلان نفس مجلد الملفات.

**ENV-04:** الدمج يحدد قاعدة المصدر وإصدار تغييرات الطرفين، واتفاق الإسناد، وفحوص النتيجة المدمجة. يحل التعارض القابل للحسم داخل النطاق ويعيد التحقق؛ يرفع القرار المؤثر أو المتناقض للمالك. لا overwrite ولا فقد تعديل غير ملتزم به دون حفظه ومعالجته.

**ENV-05:** لكل وصلة خريطة قدرات موثقة: هوية جلسات، إنشاء/استئناف عامل، نماذج، رسائل أثناء العمل، أوامر `/`، أدوات، إلغاء، compaction، وسياسات. الفجوة في سطح أصلي تحتاج امتدادًا/واجهة مدعومة واختبارًا؛ لا تسقط الميزة المطلوبة من سطح إصدار بلا إعلان ومعالجة قبل V1.

## 8. الذاكرة والقرارات والخصوصية

**MEM-01:** واجهة ذاكرة مشتركة فوق ثلاث قواعد محلية متفق عليها: `person.db` للشخص وتفضيلاته، `project.db` للمشروعات وقراراتها ومهامها وأدلتها، و`global.db` للمعرفة العامة المتحققة. المعرفات والنطاقات تمنع خلط مشروع بآخر أو مستخدم بآخر؛ «عامة» لا تعني كشف معلومات كل شخص لكل أعضاء التثبيت.

**MEM-02:** تحدّث التفضيلات والتصحيحات تلقائيًا ضمن نطاقها، ويدعم «تذكر» الصريح، مع عرض ومراجعة وتراجع. الاستنتاج عن تفضيل غير مصرح به لا يصبح قرارًا شخصيًا مؤكدًا. التعارض يحفظ مصدره وحداثته ولا يحل بتفضيل ملخص قديم على تصحيح حديث.

**MEM-03:** تنقل الدروس العامة المتحققة تلقائيًا بعد إزالة خصوصيات المشروع، مع أصل قابل للتتبع وضوابط مشاركة. المواد غير المتحققة لا تدخل كمعرفة مثبتة، ولا تنقل الأسماء أو الأسرار أو النصوص الخاصة بحجة التعلم.

**MEM-04:** الاسترجاع موجّه للدور والمهمة، مع مصادر وإصدارات وحداثة ومراجع إلى الأصل. يحافظ الضغط على الأهداف والقرارات والتوقفات والأدلة اللازمة؛ الملخص ليس الأصل. قبل تصرف يعتمد على قرار يتحقق من نسخته النشطة. يحتفظ النظام بالمعرفة طويلة الأجل دون تحميلها كلها في نافذة واحدة.

### 8.1 مسارا الإزالة

**MEM-05:** طلب النسيان/الحذف بالنص ينقل المحدد إلى الأرشيف مع إمكان الاستعادة. يخرج من الاسترجاع النشط والملخصات والفهارس النشطة، ويتوقف استخدامه كقرار حالي. إذا لم يكن المقصود محددًا، يستوضح قبل إزالة نطاق أوسع. لا يحول نص المستخدم العادي إلى محو نهائي.

**MEM-06:** أمر `/` مخصص للمحو النهائي يعرض نطاق البيانات والنسخ المدارة المتأثرة وعدم قابلية الاستعادة، ويطلب تأكيدًا صريحًا من مخول. اقتراح تسمية: `/dai-memory purge`. لا ينفذ بنص المصدر أو مخرجات وكيل أو موافقة قديمة على نطاق مختلف.

**MEM-07:** نجاح المحو النهائي يعني إزالة المحتوى من السجلات والمشتقات والفهارس/المتجهات والملفات/الأرشيفات والنسخ الاحتياطية التي تديرها D_AI ضمن النطاق المؤكد، أو جعلها غير قابلة للفك باستراتيجية محو مثبتة. لا يسجل نص المحذوف في إيصال التدقيق ولا يعيد بناءه من Cache أو نسخة قديمة عند الاسترجاع. تبطل النتائج/السياقات المدارة التي قد تعيد حقنه.

**MEM-08:** يجب أن يختار التصميم ويختبر استراتيجية محو تناسب SQLite وWAL والنسخ الاحتياطية، لا `DELETE` صف فقط. لا يعرض «اكتمل المحو النهائي» إذا بقيت نسخة مدارة قابلة للاستعادة. النسخ الخارجية التي لا تتحكم بها D_AI، بما فيها تصدير سابق للمستخدم أو سياق سبق إرساله لمزود، تظهر حدودها قبل التأكيد؛ لا يعد بمحوها عن بعد. لا ترسل النسخ الاحتياطية محتوى ممحوًا إلى الذاكرة عند restore.

## 9. اختيار النماذج والموارد

**MOD-01:** النموذج الأساسي هو اختيار المستخدم لبداية الجلسة، مع override صريح. يوزع النظام نماذج الأدوار حسب احتياج المهمة ويعلن اسمها ودورها وسبب الاختيار. الكبير يسأل عن اختياراته أثناء التأسيس؛ المتوسط والصغير يعرض اقتراحًا وفق التفضيلات والتفويض. القواعد المحفوظة تقلل إعادة الأسئلة ولا تلغي حق المستخدم في التعديل.

**MOD-02:** التوجيه يستهدف أفضل قيمة للمهمة: جودة مجرّبة مناسبة للدور، صلاحية أدوات/سياق، زمن، تكلفة وحدود اشتراك، وموارد محلية. أسماء النماذج أو قوائم مجانية أو أعداد النجوم ليست اختبار تأهيل. مجهول التكلفة لا يحسب صفرًا، والاشتراك لا يعامل كطلبات بلا حد، وظهور الكتالوج لا يثبت اتصالًا.

**MOD-03:** عند فشل معيار الجودة، يجوز انتقال معلن إلى أفضل خيار داخل القائمة والميزانية المعتمدتين. عدم توفر خيار مأذون يضع الفرع في انتظار قرار/مورد مع بدائل. لا fallback مدفوع أو تغيير أساسي أو تجديد اشتراك أو تحميل نموذج ضخم بصمت.

**MOD-04:** يقبل توجيه المستخدم أثناء التشغيل: نموذج أو توزيع عمل أو قيد جديد. يعترف بالتوجيه ويحدد الوحدات المتأثرة، ويحفظ القرار ويعيد الجدولة عند نقطة آمنة؛ لا يعد بتغيير طلب أرسل بالفعل بأثر رجعي ولا يكرر أثرًا غامضًا. يستمر العمل غير المتعارض.

**RES-01:** المال والوقت وحدود الاشتراكات والموارد تضبط لكل مشروع/مهمة؛ لم يختر المستخدم سقفًا عالميًا ثابتًا. الافتراضي `balanced` مع إعداد قابل للتغيير نحو الجودة أو التوفير؛ هذه أوضاع توزيع موارد، لا تخفيفًا صامتًا لمعيار صحة الادعاءات.

**RES-02:** يفصل القياس بين الفعلي والتقديري والمجهول: توكنات مدخلات/مخرجات وكاش حيث يبلغها المزود، تكلفة نقدية معلومة، حدود اشتراك عند توفر بيانات، زمن تنفيذ وانتظار، ومحاولات وأدوات وCPU/RAM/VRAM/تخزين. لا يُجمع رقم اشتراك وحدود نقدية أو تقديرات توكنات كنفقات متجانسة.

**RES-03:** قبل تجاوز حد العقد، ينذر ويعرض بدائل: أرخص/مجاني، انتظار، تقليل نطاق معتمد، تمديد أو توقف. المالك يقرر. حتى يصله القرار لا يبدأ طلبًا معلومًا أنه خارج التفويض؛ يسجل أي تجاوز غير متوقع من طلب جارٍ بدل إخفائه. طريقة التعامل مع الزمن والتعثر والبحث المفتوح جزء من التأسيس.

**RES-04:** يحسن الاستهلاك بتحميل مهارات وأدوات حسب الحاجة، واسترجاع محدد، ومراجع بدل نقل ملفات كاملة، وتفويض مدروس، وإعادة استعمال نتائج صالحة مع فحص نسختها، وإيقاف التكرار غير المنتج. تقاس فائدته مقابل خط أساس؛ تقصير الإجابة وحده لا يثبت خفض تكلفة العمل أو الحفاظ على الجودة.

**RES-05:** الجهاز المرجعي الحالي RAM 16GB وVRAM 6GB، مع اعتماديات يضبطها المثبت. تتكيف طوابير الاستدلال والتزامن وحجم السياق والأصول/الرندر مع قياس فعلي، وتعرض متطلبات ما لا يتسع. لا أرقام سرعة أو استهلاك معتمدة قبل القياس على هذا الجهاز.

## 10. الاستمرارية والحالات والتحديثات

**DUR-01:** يحفظ المشروع: العقد وإصداراته، القرارات، المخطط والمهام وملكيتها، الوكلاء والجلسات، المصادر والفرضيات، المخرجات والمحاولات، الصلاحيات والميزانية، الانتظارات، والحدث/الخطوة التالية. ضغط أو تبديل نموذج أو توقف لا يمحو هذه الحالة.

**DUR-02:** بعد عودة التشغيل يستأنف النظام تلقائيًا العمل المأذون الذي كان جاريًا، بعد التحقق من آخر حالة وتغير المصدر والأذونات والموارد. يميز مهمة تستأنف من بيئة جديدة تفتح للعرض وتنتظر. لا تنفيذ حين يكون المضيف مطفأ ولا وعد باستمرار سحابي في V1.

**DUR-03:** لكل طلب/أثر معرف منع تكرار وسجل حالة. انقطاع بعد الإرسال وقبل النتيجة يؤدي إلى تحقق/مصالحة، لا إعادة إرسال تلقائية غامضة. تختبر الانقطاعات قبل وبعد الحجز والإرسال والحفظ والدمج والمحو والتحديث.

**DUR-04:** الحالات الدنيا: `DISCOVERING / WAITING_FOR_INPUT / PLAN_REVIEW / READY / RUNNING / VERIFYING / REVIEWING / WAITING_FOR_HUMAN / WAITING_FOR_MODEL / WAITING_FOR_DATA / WAITING_FOR_RESOURCES / PAUSED / RECOVERING / COMPLETED / PARTIAL / FAILED / CANCELLED`. انتقال لحالة إتمام يحتاج المخرجات والفحوص ومعالجة الملاحظات والحدود حسب العقد. `PARTIAL` لا يرمز خفية إلى نجاح كامل.

### 10.1 مراقب تحديث GitHub

**UPD-01:** المصدر الافتراضي D_AI فقط. إضافة مستودعات/مكونات للمراقبة اختيار مستخدم. مصدر المستودع وقناة الإصدار/الفرع/الالتزام مثبتان في إعداد الإصدار؛ لا يعتمد على مستودع تجريبي موروث.

**UPD-02:** عند التشغيل الأول دون فحص سابق ينفذ تحققًا. بعده، إذا `وقت التشغيل >= وقت آخر فحص ناجح + 7 أيام` ينفذ فحصًا واحدًا عند أول تشغيل مستحق. التشغيل قبل ذلك لا يفحص تلقائيًا. أسبوع انقضى والجهاز مطفأ لا يولد فحوصًا فائتة متراكمة. يسمح بفحص يدوي وتغيير الإعداد.

**UPD-03:** يخزن وقت آخر نجاح ونتيجته والمعرف المرصود؛ فشل الشبكة لا يوصف نجاحًا ولا يؤجل الفحص أسبوعًا كاملًا كأنه نجح. يسجل الخطأ ويعيد وفق محاولات محدودة/التشغيل التالي. تشغيل عدة بيئات لا يولد فحصًا مكررًا بفضل تنسيق محلي واحد.

**UPD-04:** عند تحديث جديد يعرض النسخة/الالتزام والفروق ومصدرها والجديد وأثر التوافق/الترحيل/الموارد، ثم خيارات تحديث أو تأجيل أو تجاهل الإصدار. لا إشعار متكرر بنفس النتيجة دون تغيير؛ قناة العرض من البيئة النشطة مع سجل محلي. ليس هناك جدولة في Codex ناتجة عن هذا المتطلب.

**UPD-05:** كل إضافة أو تحديث للتفعيل يحتاج قرار المستخدم، ثم حفظ إمكانية الرجوع وفحص التوافق وترحيل البيانات واختبارات ملائمة قبل اعتماد النسخة. إذا فشل التحديث يحفظ الوضع السابق أو يسترده دون فقد بيانات، ويعرض الإيصال؛ العثور على إصدار أحدث ليس إذن تثبيت.

## 11. قدرات الأنظمة التخصصية ومواصفات الفروع

**SYS-01:** الأنظمة العشرة المعرفة حاليًا كلها ضمن هدف V1: البحث العلمي، الابتكار، التعلم، الاستثمار، المساعد الشخصي، التحقيق، الأمن السيبراني، التحليل الاستراتيجي والعسكري، المستشارون، والهندسة. العدد والأسماء لا يقفلان التوسع؛ دور جديد أو فرع جديد يُشتق من حاجة المهمة، مع تعريف قابل للفحص وتفويض وأدوات مناسبة.

**SYS-02:** لكل نظام سجل قدرات وفروع، ومواصفات منهج وأدوار وأدوات ومهارات ومدخلات ومخرجات، وأمثلة صحيحة وحالات مضادة وأدلة قبول. الصفة `CONFIGURED` لا تعني اختبار المجال مهنيًا. يحافظ سجل V1 على كل قدرة متفق عليها، ويمنع إسقاطها إلى هيكل أو stub لتسمية المنتج مكتملًا.

| المساعد الشخصي | أهداف ومهام ومواعيد ووثائق ومراسلات ومتابعات ومعرفة شخصية وتنسيق مشروعات | اقتراح جدول غير تعديل تقويم، وإعداد رسالة غير إرسالها، وتنسيق عمل غير تغيير هدفه | خطة قابلة للتنفيذ، تعارضات وقيود معلنة، سجل ما أُعد وما نُفذ فعليًا، متابعة بإذن ودون تكرار إجراء |
| التحقيق والاستقصاء | تقييم مصادر ووقائع، كيانات وعلاقات وخط زمني، فرضيات متنافسة، وثائق ووسائط وبيانات جغرافية حسب المدخل | التحقق من ادعاء غير حل تطابق كيان أو تحليل تغير زمني أو فحص مادة إعلامية | أصل ومكان وتاريخ كل دليل، فرق التكرار والاستقلال، درجة ثقة مبررة، فصل علاقة رصدية عن استنتاج، ملف قضية قابل للمراجعة |
| الأمن السيبراني | فهم أصول وتهديدات، كود وتكوين واعتماديات وهوية وشبكات، فحص نتائج، حادث وجنائي، إصلاح واستعادة وإعادة اختبار | مراجعة تطبيق غير فحص شبكة أو تحليل حادث أو forensic؛ التفويض والمصدر وحفظ الدليل ومنهج التحقق يناسب الفرع | دليل قابل للإعادة، false-positive مقابل confirmed، أثر وأسباب وإصلاح وفحصه، ربط الفعل بنطاقه الفعلي وسياسة المستخدم دون حظر باسم المجال وحده |

| المستشارون الشخصيون | مالي وقانوني وإداري ومحاسبي، مع تخصصات لازمة للمهمة | ميزانية وسيولة غير عقد وولاية وتاريخ، وغير SOP وموارد، وغير قيود وتسويات وإغلاق | أصول حسابات ومستندات، مصادر ملائمة محدثة عند التنفيذ، مخرجات قابلة للتطبيق والمراجعة، اختلاف أو تعارض الاختصاصات معلن ومحلل |
| الهندسة والإنتاج الرقمي | متطلبات وتجربة ومعمارية وبيانات وواجهات، تنفيذ وفحص وتشغيل، تصميم وصور وحركة وفيديو وSEO/GEO عند الحاجة | بناء جديد غير إصلاح أو ترحيل، منتج ويب غير CLI أو خدمة، صورة غير موشن أو تحليل ظهور | برنامج/أصل يعمل، فحوص واستخدام فعلي، حالات فشل وحواف وأداء وإتاحة حيث تنطبق، مصادر قابلة للتحرير وإعادة الإنتاج |

**SYS-03:** خريطة الفروع التفصيلية تُبحث وتُسجل في مواصفات الأنظمة قبل تطويرها؛ ليست مهمة المستخدم تعداد كل مهارة أو اختيار مكتبة. كل فرع معلن في V1 يربط بمنهج وأداة/تنفيذ واختبار قبول وأدلة. فرع مستحدث أثناء مشروع يحتاج مسار WFL-05، ولا يبرر ادعاء أنه اجتاز قبولًا سابقًا.

**SYS-04:** قبل أي دمج عابر للمجالات، تفحص توافق المفاهيم والوحدات والزمن والجمهور/العينة والمصادر. تفاعل البحث والتحري أو المالي والقانوني أو التصميم والهندسة لا يعني دمج نتائج متناقضة في ملخص واثق.

## 12. مسار قبول مرجعي: أفكار بحث علمي في الطب والذكاء الاصطناعي

هذا المثال مأخوذ من المالك لقياس العمق، وليس بحثًا طبيًا منفذًا أو وصفة واحدة لكل دراسات الطب. الناتج المطلوب مقترحات حقيقية محددة وغير مبتذلة، مدعومة بفهم الأدبيات الحديثة وفجواتها ومعضلاتها وتناقضاتها وأسئلتها المفتوحة.

### 12.1 بروتوكول المهمة

**SCI-01 — تأطير السؤال:** يفحص ما هو معروف عن المشروع ثم يسأل عن المجال الطبي والفئات/المشكلة ونوع تطبيق AI والنطاق الزمني والأدلة المتاحة والجمهور العلمي والوقت والتكلفة. يفصل الرغبة عن قيد لم يصرح به المستخدم؛ يطلب تحديده عند تأثيره. في هذا المثال تُقبل فئتا أفكار: ممكنة بموارد المالك وأخرى تحتاج موارد إضافية معلنة.

**SCI-02 — خطة أدبيات مناسبة:** يحدد فهارس ومصادر ونصوص ومصطلحات وعلاقات تخصصية ومعايير انتقاء وتغطية مناسبة لنوع البحث. يوثق الاستراتيجية وتاريخ البحث والتحديث. تنوع محركات البحث أو كثرة الروابط لا يثبت تغطية الأدبيات؛ يعلن حدود الاسترجاع والنصوص غير المتاحة.

**SCI-03 — قراءة منظمة:** يربط الدراسات المتكررة أو المشتركة في البيانات، ويستخرج السؤال والمنهج والعينة/السياق والبيانات والنموذج والمقارنات والنتائج وعدم اليقين والقيود وملاحظات المؤلفين. يحفظ موضع كل معلومة، ويفرق بين ملخص ونص كامل وملحق وبيانات تجريبية.

**SCI-04 — تحليل جودة وتعارض:** يقارن ملاءمة التصميم والقياس والتحيز وجودة البيانات والتحقق الخارجي والتعميم والتسرب والعوامل المربكة وفق موضوع الدراسة. نتيجة رقمية مختلفة لا تُسمى تناقضًا قبل فحص السكان والمهمة والبيانات والمقياس والمنهج. يميز فجوة صرح بها المصدر من فجوة استنبطها النظام ومن نقص وصول إلى الأدبيات.

**SCI-05 — خريطة فرص:** ينظم ما ثبت وما اختلف عليه وما بقي مفتوحًا والقيود المنهجية والعملية والتناقضات القابلة للفحص. يربط فرصًا بين الطب وAI بآلية أو حجة محددة، ويفحص العمل الأقرب الذي قد يغطيها، بما فيه الدراسات غير المؤيدة أو الناقضة المتاحة.

**SCI-06 — بناء المقترح:** لكل فكرة: مشكلة وفجوة ومصادر، أهمية وسؤال/فرضية قابلة للاختبار، العمل الأقرب والفارق عنه ضمن حدود البحث، منهج وبيانات ومقارنات وخطة تقييم، متطلبات إتاحة وتجارب/بشر، مخاطر وتسرب/تحيز وعدم يقين، ما قد يبطل الفكرة، وخطوة أولى قابلة للتنفيذ. تختلف التفاصيل حسب الفرع؛ لا تلحق أسماء نماذج رائجة بفكرة عامة لتسميتها بحثًا جديدًا.

**SCI-07 — الجدوى والترتيب:** يصنف المقترحات إلى مناسبة للموارد الحالية وأخرى تحتاج بيانات/تعاونًا/مختبرًا/عتادًا/تمويلًا إضافيًا. يذكر ما يحتاجه كل مقترح صراحة، ويميز تقدير تكلفة من عرض سعر. يبرر ترتيب القيمة العلمية والجدوى والمخاطر؛ يحدد المستخدم عدد المقترحات أو يتفق عليه في العقد بدل رقم عالمي مخترع.

**SCI-08 — نقد ومراجعة:** مراجع أدلة ومنهج يفحص المصادر والادعاءات، وناقد جدة/جدوى يراجع العمل الأقرب وقابلية الاختبار. تتاح مادة المصدر والخطوات للمراجعة؛ لا تختزل إلى تقييم لغوي. يعاد بناء/استبعاد المقترح الضعيف أو يصنف مبدئيًا، وتبقى ملاحظات الاعتراض مرئية.

### 12.2 التسليم والقبول

يسلّم تقرير الفرص، وبطاقات المقترحات، وخريطة الأدلة والفجوات والتناقضات، واستراتيجية البحث، ومراجع الأصل وحدود الوصول، ومتطلبات التنفيذ والخطوات التالية. يسمح بالتحديث الطويل حين تظهر أوراق أو تجارب جديدة وفق عقد المشروع.

**SCI-09:** بوابات قبول قاطعة: لا استشهاد مختلق؛ لا نسبة قراءة نص كامل غير مقروء؛ لا ادعاء مثبت بلا سند؛ لا ادعاء جِدة عالمية مطلقة من بحث محدود؛ لا تجربة أو نتيجة مختلقة؛ لا اقتراح عام بلا فجوة محددة ومنهج اختبار. فرضية مصرح بها ومبررة ليست نتيجة مثبتة، ويمكن أن تنتهي التجربة بإبطالها دون تغيير تاريخها.

**SCI-10:** الجودة تقاس على ملاءمة الفجوة وقوة الدليل وخصوصية الفكرة وقابليتها للاختبار والجدوى وشفافية الحدود، مع rubric معلن ومراجعة المجال. لا تعوض نسبة متوسط عالية وجود استشهاد مختلق أو انتهاك بوابة قاطعة. لم تنفذ هذه القياسات في مرحلة إعداد PRD.

## 13. مسار قبول مرجعي: الصورة والموشن جرافيك

المطلوب قدرة إنتاج أعمال المستخدم، ومنها فيديو بـRemotion، بجودة تكوين وحركة وتسلسل وعناصر ونصوص وتوقيت تناسب عملًا مهنيًا. [المراجع العشرة](VISUAL_REFERENCES_AR.md) توثق الصفحات والإطارات التي شوهدت وحدود مشاهدة الحركة؛ لا تُستنسخ منها الأصول أو الهوية لكل عمل.

**VIS-01 — بناء brief:** الهدف والرسالة والجمهور والمنصة والأبعاد واللغة والهوية والمراجع والمدة/عدد النسخ والصوت والأصول المتاحة والحقوق والموارد والتسليم. يسأل عن القرار الناقص بدل افتراض ذوق المستخدم من قالب عام. تختلف فروع الصورة والتحرير والموشن والسرد/إعلان المنتج والبيانات المصورة.

**VIS-02 — الاتجاه الفني:** يقترح مبررات لوحة/طباعة/تكوين وشبكة ونسب وهرمية قراءة وعمق وإضاءة وخامات أو أسلوب تصوير مناسب. ينشئ عينات اتجاه فني للمقارنة والمراجعة؛ كون مرجع المستخدم داكنًا أو مضيئًا لا يفرض هذا الأسلوب على موضوع مختلف.

**VIS-03 — الاعتماد البصري:** يعتمد المستخدم عينة اتجاه فني، وتخطيط مشاهد/storyboard أو animatic حين ينطبق، قبل الإنتاج النهائي. يسجل الاعتماد وما يغطيه؛ تعديل كبير في الرسالة أو الأسلوب يعود للقرار، وتصحيح عيب ضمن المعتمد لا يعيد كل موافقات المشروع تلقائيًا.

**VIS-04 — تصميم الصورة:** يعمل على التكوين ومحاذاة وتباعد ونسب وتسلسل بصري وطباعة/لغة ووضوح في المقاس النهائي. يختار بناء متجهي/كود أو أدوات صور/تحرير أو أصولًا مناسبة، ولا يقيس جودة التصميم بجودة برومبت التوليد وحدها. يراجع الصورة المرئية الفعلية ويعالج التشوهات والحروف والأخطاء الدلالية.

**VIS-05 — تخطيط الفيديو:** يربط الرسالة بقوس سرد ومشاهد ومدة قراءة وحركة كاميرا/عناصر وانتقالات وصوت إن طُلب. يضع لغة حركة: تسارع/تباطؤ، فواصل/تداخلات، استمرارية أماكن وأشكال، وزن واتجاه وعمق. ليست كل لقطة fade أو كل تأثير مناسبًا لكل مشهد؛ لكل اختيار وظيفة في التسلسل.

**VIS-06 — تنفيذ Remotion:** يحول الخطة المعتمدة إلى مشروع منظم بمكونات ومشاهد وخط زمني وأصول ومعلمات قابلة للتحرير. يختار المكتبات وفق الحاجة والتوافق بدل تحميل GSAP/Motion/Anime وغيرها جميعًا في كل عمل. يفحص التوقيت والإطارات ومعدل الإطارات والأبعاد والخطوط والأصول الناقصة والشفافية/الصوت حيث ينطبق. الأداة المختارة لا تضمن وحدها جودة الحركة.

**VIS-07 — مراجعة متعددة المستويات:** معاينة صور/إطارات، مشاهدة التسلسل المتحرك نفسه، مقارنة بالمراجع المعتمدة، فحص لغوي/قراءة، تداخل أو قص أو اهتزاز أو قفزات زمنية، إيقاع وتماسك انتقالات، وتزامن الصوت وجودته حيث ينطبق. يبقى تحقق زمني `NOT_RUN` إذا لم يستطع المراجع تشغيل الفيديو؛ لا تستبدله لقطات ثابتة.

**VIS-08 — التسليم:** الصورة/الفيديو النهائي بصيغ العقد، والمشروع القابل للتحرير، والأصول/مراجعها وحقوق استخدامها، والخطوط اللازمة المسموح بتوزيعها، وإعدادات الرندر/الإصدارات وتعليمات إعادة الإنتاج. يوضح ما لا يجوز تضمينه أو يحتاج وصول المستخدم؛ لا يسلّم مشروعًا يفتقد أصلًا لازمًا دون بيان.

**VIS-09:** قبول الصورة يشمل التكوين والدقة والهرمية والقراءة والملاءمة والأمانة للمحتوى والاعتماد البصري. قبول الفيديو يضيف السلاسة والتوقيت والاستمرارية والتسلسل والصوت عند طلبه. نجاح الرندر بوابة تقنية فقط؛ وصف احتراف يمر بمقارنة بصرية/زمنية ومعيار معتمد. لا معيار مفروض بأن «أكثر مؤثرات = أفضل».

## 14. الأدوات والمهارات والمكونات الخارجية

**EXT-01:** تصنف الموارد إلى معرفة/منهج، مهارة، أداة أو موصل، مكتبة تنفيذ، أصل بصري، مرجع ذوق، أو إطار تشغيل. كل مصدر من قائمة المالك يحصل على قرار تبنٍّ موثق أو بديل/تكرار/مرجع أو سبب انتظار؛ لا يتبع الاسم قرار تنزيل أو تنشيط شامل.

**EXT-02:** لكل مرشح: المشكلة التي يحلها، المقارنة بالموجود والبدائل، المصدر والنسخة/البصمة، الرخصة والإشعارات المنطبقة، الصيانة والتوافق، متطلبات التشغيل، أثر الموارد والسياق، بيانات يقرأها/يرسلها، تعليمات متعارضة، واجهات ومخرجات وفشل، واختبارات قبول. مقياس ثابت أو ماسح أمن أو `origin` وحده لا يكفي لاعتماد أو رفض قانوني/جودة شامل.

**EXT-03:** تفحص المواد في مساحة معزولة عن التحميل النشط، ثم تراجع وتختبر ويوافق المستخدم قبل التفعيل. يحفظ القفل والنسخ وإمكان الرجوع. محتوى ECC المقتنى محليًا لا يدخل سياق الجلسات أو حساب المهارات المفعلة لمجرد وجوده داخل `packs/`.

**EXT-04:** الدمج الفعلي يربط المهارة/الأداة بشرط استدعاء ومسؤولية في منهج النظام، ومدخلات ومخرجات واضحة، وسياسة وحالات فشل وتحقق ومراقبة. لا يركب منسقين متنافسين لنفس العمل أو يكرر سياسات متعارضة بين مهارات. لا يقبل تعليمات مصدر تنقل سلطتها فوق قرارات المالك أو سياسة المشروع.

**EXT-05:** تحمل الموارد عند الحاجة؛ الفهرسة القصيرة غير حقن كل النصوص والأدوات. تفصل قواعد التخصص عن النواة المشتركة، وتولد/تربط تعريفات البيئات من أصل واحد بدل نسخ يدوية تنحرف. اختبار المهارة يشمل عدم استدعائها عندما لا تناسب المهمة، وفشلها دون اختلاق نجاح.

**EXT-06:** تثبت فائدة المكون بمهمة قبل/بعد أو مقارنة مناسبة عند تعذر إعادة الحالة، على نفس المدخلات والميزانية/الشروط قدر الإمكان. تسجل الجودة والكلفة والزمن والتراجعات؛ يرفض تدهور غير مفسر أو يرجع النسخة. لا تدخل ميزة قائمة V1 المتاحة دون مسار مستخدم فعلي مختبر.

## 15. البيانات والواجهات والسجل المطلوب

**DAT-01:** كيانات المنتج الدنيا: مستخدم/فريق/تفويض؛ مشروع/نسخة عقد/قرار؛ مهمة/خطة/خطوة/محاولة؛ وكيل فريق/جلسة مضيف/استشارة؛ نموذج/ملف قدرة/اختيار/استخدام؛ مصدر/ادعاء/دليل/فرضية؛ مخرج/إصدار/فحص؛ رسالة/اقتراح/اعتماد؛ أرشيف/طلب محو/إيصال؛ مكوّن/نسخة/قفل؛ وفحص تحديث/نتيجة/قرار تثبيت.

**DAT-02:** شجرة ملكية الوكلاء، ومخطط تبعيات المهام، وعلاقات الأدلة، وهويات جلسات المضيف مفاهيم مستقلة مترابطة بمعرفات. لا يُستنتج تقدم المهمة من وجود ابن في شجرة الوكلاء، ولا أصل الدليل من نص ملخصها.

**DAT-03:** واجهات النواة تشمل إنشاء/تعديل عقد وقرار مخول، قراءة/استرجاع ذاكرة ضمن نطاق، إسناد/حجز عمل واستلام نتيجته، استشارة وإرسال اقتراح، اختيار/تغيير نموذج، قياس مورد، انتظار/استئناف، أرشفة/استعادة/محو مؤكد، فحص تحديث/عرضه/اعتماده، وتصدير/نسخ/استعادة بيانات محلية. يثبت مخطط الطلب/النتيجة/الأخطاء والإصدار في التصميم قبل ربط الوصلات.

**DAT-04:** واجهة العرض تميز الحالة والنتيجة والسبب: نموذجه ودوره، تعاون نظام آخر، خطوات قائمة، مال/وقت معلوم أو مقدر، انتظار مؤثر، قرارات معلقة، وأدلة الإتمام. شفافية لا تعني كشف أسرار أو تفريغ تفكير داخلي؛ يعرض الخطة والأفعال والأسباب والأدلة اللازمة للمراجعة.

**DAT-05:** العربية والإنجليزية والنص المختلط والكود والأرقام والمسارات قابلة للقراءة في أسطح V1، مع مراعاة RTL/LTR وفق قدرات المضيف والتحقق الفعلي. التحكم المطلوب متاح بأوامر `/` والتفاعل الأصلي حيث يلائم؛ لا يعتمد نجاح سير العمل على بناء تطبيق واجهة مستقل لم يطلبه المالك.

## 16. بنية مستودع قابلة للقراءة

**REP-01:** أصل وظيفي واحد لكل حقيقة/تعريف؛ تقسيم حسب المسؤولية، وثائق دخول قصيرة وروابط للمواصفات بدل كتل مكررة، وأسماء متسقة بين الكود والعقود والمهارات. الشجرة التالية **اقتراح تنظيمي**، وليست عملية نقل نُفذت:

```text
D_AI/
  README.md                 # دخول عربي وروابط التشغيل والحالة
  README.en.md
  INSTALL.md
  CONTRIBUTING.md
  SECURITY.md
  THIRD_PARTY.md
  LICENSE
  GLOSSARY.md
  src/
    core/                   # العقود والقرارات والخطط والتفويض والسياسات
    memory/                 # الشخص والمشروع والعامة والأرشفة والمحو
    teams/                  # الوكلاء والرسائل والاستشارات وملكية العمل
    models/                 # القدرات والاختيارات والقياس
    tools/                  # بوابة الأدوات وربط التنفيذ
    updates/                # فحص GitHub والتثبيت والرجوع
  adapters/
    opencode/
    pi/
  systems/                  # مواصفات وقدرات ومناهج الأنظمة
  packs/                    # حزم قدرات محددة المصدر والنسخة
  config/                   # مخططات وقيم عامة وأمثلة دون أسرار
  scripts/                  # إعداد وفحص وترحيل وتغليف
  tests/                    # عقود ووصلات واستمرارية ومجالات ومخرجات
  docs/
    MAP_AR.md
    PRD_D_AI_V0.1_AR.md
    architecture/
    workflows/
    systems/
    decisions/
    evidence/               # إيصالات قابلة للنشر بعد إزالة البيانات الخاصة
    discovery/              # نقل منظم لمحاضر الاكتشاف عند تثبيت المرجع
```

**REP-02:** بيانات المستخدم والجلسات والذاكرة والمشروعات والأسرار والمخرجات الخاصة خارج شجرة النشر. `~/.d-ai/` هو مجلد البيانات المركزي المقترح سابقًا مع مسار قابل للضبط؛ الوصلات تستخدم نفس الجذر. ليست هناك هجرة تلقائية لبيانات المستخدم لمجرد تغيير تنظيم المصدر.

**REP-03:** الأرشيف القديم يبقى خارج المستودع مع فهرس ومصدر استعادة، ولا يعود إلى شجرة النشر أثناء التنظيم. الحزم الخارجية لها مصدر وقفل ومراجعة ومكان واضح؛ لا نسخ من مستودعات كاملة داخل كل نظام. نقل الملفات في دفعات قابلة للرجوع، بفحص المسارات والروابط والتشغيل.

**REP-04:** يستمر المستخدم بتخصيص نماذجه وملفاته عند التثبيت/التحديث. المثبت يفحص النسخ والموارد والتوافق والاتصالات المطلوبة، وينشئ ملف تعريف صغيرًا لكل بيئة. الأوامر المقترحة مثل `setup --env …` لا تصبح طريقة مدعومة قبل اختبار تثبيت بارد وترقية ورجوع لكل سطح.

**REP-05:** قرارات المشروع المسجلة: مستودع GitHub مستقل باسم D_AI، ونشر بعد اكتمال V1، ورخصة D_AI هي GPL-3.0-or-later، ومساهمات خارجية تمر بمراجعة المالك قبل الدمج. تحفظ نسب المكونات ورخصها وإشعاراتها الخاصة، ولا تعاد نسبة محتوى خارجي إلى D_AI أو يعد وجوده تصريحًا بإعادة توزيعه.

## 17. توجيه معماري ومقارنة بالوضع القائم

الاقتراح المعماري: نواة تنسيق وحالة وذاكرة وسياسة مشتركة، ووصلات تنفذ عبر الجلسات وحلقات النماذج الأصلية للمضيفين. لا يعني ذلك Fork جديدًا من Harness أو إضافة حلقة LLM متنافسة خفية. يحتاج التصميم التفصيلي ADRs عند المقايضات الصعبة، واختبار حدود واجهات OpenCode وpi المحددة قبل اعتمادها.

| الفرق المطلوب | الدليل المقروء في التنفيذ الحالي | المطلوب قبل قبول V1 |
|---|---|---|
| عدة بيئات | التخصيص والراوتر وأدوات البيانات مرتبطون بـOpenCode | عقود مشتركة ووصلتا OpenCode وpi، والتحقق على أربعة أسطح |
| فريق مستمر وثلاث طبقات | الراوتر الحالي يقيد إعادة تفويض العامل | هوية فريق ورسائل وعمر مشروع وتفويض محدود بالموارد، مع فحوص عدم الدوران |
| استشارة ضمن جلسة | القدرة المطلوبة لا يثبتها مجرد subagent منتهٍ بالمهمة | أمر وتفاعل وحالة فرعية وتحديث معرفة ومسار رسالة للقائد، وفصلها عن جلسة جديدة |
| ذاكرة موحدة قابلة للمحو | SQLite الموجودة تحفظ مهام وأدلة، والمضيف يملك جلساته | فصل النطاقات الثلاثة وفهارس واسترجاع وقرارات وإصدارات وأرشفة ومحو جميع النسخ المدارة |
| توزيع كفء حسب المهمة | الفئات الحالية ثلاث، والتصنيف اللغوي محدود | توصيف دلالي ومنهجي واختبارات قدرة وكلفة وإتاحة مع إعلان وتعديل حي |
| قدرات مهنية كاملة | كتالوج الأنظمة يصرح `professional_validation: NOT_COMPLETE` | مصفوفة قدرة/فرع/أداة/مهارة واختبارات ومخرجات مهنية، لا الاكتفاء بجرد التعريفات |
| تحديث أسبوعي عند تشغيل مستحق | لم يُثبت هذا السلوك الجديد | خدمة فحص محلية منسقة وحالة وقت/نتيجة وموافقة وترحيل ورجوع |

هذه قراءة ملفات، لا فحص تشغيل جديدًا أو وصفًا شاملًا لكل ما تغير في جلسات أخرى. المكونات السابقة يعاد استعمالها حيث توافق العقد الجديد ويثبت سلوكها؛ لا يعاد بناء الصحيح بلا سبب ولا يستمر القيد القديم بحجة وجوده.

### 18.1 تصميم المقارنة والكفاءة

تقارن مهام مرجعية ثابتة بمخرجات نموذج مباشر وبنفس النموذج داخل D_AI، ثم بدائل اقتصادية مؤهلة حيث يتاح ذلك. تضبط المدخلات والأدوات وحدود الموارد وتكرر الحالة عند تقلب النماذج؛ توثق ما لم يمكن ضبطه. لا يعد اختلاف النموذج دليلًا على أثر الغلاف وحده.

تعتمد rubrics لكل نوع: صحة/مصدر/دعم، تحقق قابل للإعادة، ملاءمة منهج، اكتمال ومعالجة حالات، أو جودة بصرية/زمنية. يقاس الاستهلاك والوقت والكلفة مع الجودة، وتبقى البوابات القاطعة مستقلة عن المتوسط. مقارنة بخبير بشري لا تدعى دون مرجع وخبرة ومهمة وظروف تقييم معلنة. لا حدود نجاح رقمية مختلقة في هذه الوثيقة؛ تُحدد قبل تنفيذ بروتوكول المجال وتراجع معاييرها حسب المهمة.

## 19. الإطلاق وتسلسل الإنجاز

المراحل التالية ترتيب عمل داخلي وليست تقسيمًا وافق عليه المالك لنشر core/full:

1. توحيد القرارات ومواصفات القدرة والفرع والعقود، وخريطة الحالي مقابل المطلوب، واختبار صلاحية واجهات البيئتين وتثبيت نسخها المرجعية.
2. بناء مسار رأسي فعلي: تأسيس مهمة، توزيع معلن، عمل وأدلة، استشارة ورسالة قائد، قرار محفوظ واستئناف؛ ثم نقله عبر الأسطح الأربعة.
3. توسيع الفريق والطبقات والذاكرة والنطاقات والتنسيق وGit والمحو والتحديث، مع حالات الفشل والسباقات والترحيل.
4. استكمال جميع الأنظمة والمهارات والأدوات المعلنة في مصفوفة V1 ومناهج فروعها، ودمج الموارد ذات الفائدة بعد الفحص والقرار، وتنفيذ مثالي المالك وبقية حالات المجال اللازمة.
5. تثبيت نظيف وتغليف ووثائق ونسخ/استعادة وترقية ورجوع، وإغلاق نتائج الاختبارات والتراجعات، ثم نشر V1 الكاملة عند استيفاء القبول.

لا تمحو مرحلة متأخرة اختبار سلوك مبكرًا؛ ولا تعوّض كثرة اختبارات الوحدات غياب مهمة مهنية أو إثبات وصلة. يمكن تنفيذ الفروع المستقلة بالتوازي وفق عقود وملكيات واضحة.

### 19.1 بوابة نشر V1

- كل مطلب وقـدرة وفرع معلن للإصدار له تنفيذ مربوط واختبارات وإيصالات حالية؛ لا `FOUNDATION` أو fixture-only يقدم كاملًا.
- الأسطح الأربعة تجتاز الحالات المناسبة، بما فيها الاستشارة والقرار والنموذج والاستئناف والتنسيق؛ قيد API مثبت لا يختفي بتغيير وصف المطلب.
- السيناريوهان المهنيان من المالك وبقية مصفوفات الأنظمة يجتازان معايير اختصاص حقيقية، وبوابات الأدلة والمخرجات لا تُختزل إلى علامات schema.
- لا فقد بيانات أو أثر مكرر أو تسريب نطاق أو إنفاق خارج التفويض في حالات القبول، والمحو النهائي لا يعلن مع استعادة مدارة ممكنة.
- الموارد والكلفة والزمن والحدود موثقة من التنفيذ، وتغير الإتاحة أو الاشتراك يعالج بوضوح دون تجديد أو fallback غير مفوض.
- التوثيق والتركيب والتنظيم والمصدر/الرخصة والقفل والترحيل والنسخ والرجوع متحققة، وحزمة النشر خالية من بيانات المستخدم والأرشيف الخاص.
- مصدر التحديث الرسمي وقناته محددان، وفحص الأسبوع والإشعار والموافقة والرجوع مختبرة.
- حالات عدم التنفيذ/الفشل المهنية لا تخفى في متوسط نجاح، وتظهر حدود كل نتيجة عند التسليم.

يلزم قبل التنفيذ التفصيلي تثبيت schema وواجهات النواة والوصلات، وقرارات صعبة في ADR، ومصفوفة قدرات/فروع الأدوات والمهارات لكل نظام، واستراتيجية المحو والنسخ الاحتياطي المثبتة، وبروتوكولات تقييم المجال والموارد. هذه مخرجات تصميم وتنفيذ قابلة للمراجعة، وليست أسئلة تأسيس أعيد طلبها من المالك أو موافقات مخفية.

لا توجد في هذه الوثيقة إيصالات اختبار سلوك جديد. قرارات المالك مكتملة بالنسبة إلى دفعتَي الأسئلة؛ أي اختيار تقني مقترح يثبت بوصفه اقتراحًا ويقارن ببدائله، وأي اكتشاف يغير الهدف/النطاق/الإنفاق يعود إلى صاحب القرار وفق التفويض.
